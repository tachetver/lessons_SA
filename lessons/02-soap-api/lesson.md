# Теоретическая справка: SOAP API в System Design

## 1. Архитектурная философия
*   **Single Endpoint:** В отличие от REST, SOAP использует один URL на сервис (обычно `POST`). Маршрутизация к конкретному методу происходит через XML-тег внутри `<Body>` или HTTP-заголовок `SOAPAction`.
*   **Contract-First:** Разработка начинается со строгого контракта. **WSDL** описывает доступные методы и эндпоинты, **XSD** (XML Schema) описывает типы данных. Код клиента и сервера генерируется из этих схем автоматически.
*   **Тяжеловесность:** Накладные расходы XML (теги, пространства имён) делают протокол неподходящим для мобильных сетей и IoT, но идеальным для Backend-to-Backend-интеграций, где важна надежность, а не экономия трафика.

## 2. Структура сообщения
Любой SOAP-запрос и ответ обернуты в строгую иерархию:
*   `<Envelope>` — обязательный корневой элемент.
*   `<Header>` — метаданные (токены авторизации, traceId, маршрутизация).
*   `<Body>` — бизнес-логика (вызов метода и аргументы).
*   `<Fault>` — стандартизированный блок для описания исключений и ошибок.

## 3. Преимущества XSD перед JSON Schema
*   **Богатая типизация:** Наличие `xs:decimal` (критично для денег, нет потерь точности как в `float`), `xs:dateTime`, `xs:base64Binary`.
*   **Namespaces (Пространства имен):** Позволяют безопасно комбинировать схемы из разных микросервисов без конфликта имен тегов.
*   **Валидация на уровне протокола:** XML-парсер отсекает невалидные данные до попадания в бизнес-логику сервера.
*   **Наследование:** Поддержка `extension` и `restriction` для создания сложных полиморфных структур.

## 4. Ключевые паттерны проектирования (System Design)
*   **Обработка ошибок:** Ошибки бизнес-логики (например, "Недостаточно средств") не возвращают HTTP 400. Сервер возвращает HTTP 500 (в SOAP 1.1) или HTTP 200 (в SOAP 1.2) с блоком `<soapenv:Fault>`, содержащим `faultcode` и `<detail>`.
*   **Пагинация:** Реализуется через передачу сложного объекта в Body (например, `<Paging><PageSize>50</PageSize></Paging>`), а не через URL-параметры.
*   **Версионирование:** Осуществляется либо через разные URL (`/soap/v1`), либо через смену XML namespace (`xmlns:bank=".../v2"`).

## 5. Семейство стандартов WS-* (Enterprise-фичи)
Главная причина использования SOAP в корпоративной среде:
*   **WS-Security:** Сквозное (End-to-End) шифрование и цифровая подпись отдельных элементов или всего тела XML-документа, а не только канала связи (TLS).
*   **WS-AtomicTransaction:** Поддержка распределенных ACID-транзакций поверх HTTP.
*   **WS-ReliableMessaging:** Гарантированная доставка сообщений в условиях нестабильных сетей.
*   **WS-Addressing:** Асинхронная маршрутизация и поддержка паттерна "запрос-ответ" через вебхуки.

## 6. Матрица выбора: SOAP vs gRPC vs REST

| Критерий | SOAP | gRPC | REST (JSON) |
| :--- | :--- | :--- | :--- |
| **Основной use-case** | Enterprise, Банки, Legacy, B2B | Internal микросервисы, High-load | Web, Mobile, Публичные API |
| **Транспорт и Формат** | HTTP/1.1, XML (текст) | HTTP/2, Protobuf (бинарный) | HTTP/1.1, JSON (текст) |
| **Безопасность** | WS-Security (подпись полей) | TLS (защита канала) | TLS + OAuth2/JWT |
| **Транзакции (ACID)** | Встроено (WS-Atomic) | Нет | Нет |
| **Streaming** | Нет | Да (4 типа стриминга) | Частично (SSE, WebSockets) |
