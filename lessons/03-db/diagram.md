## Краткая рекомендация по построению ERD / модели данных

В рамках дисциплины **System Design** при проектировании модели данных рекомендуется разделять **концептуальный** и **логический** уровни моделирования.

### 1. Концептуальный уровень — диаграмма Чена

Для моделирования концептуального уровня рекомендуется использовать **диаграмму Чена** — классический инструмент описания предметной области без привязки к конкретной СУБД.

Диаграмма Чена позволяет показать:

- **сущности** — основные объекты предметной области, например `Пользователь`, `Заказ`, `Товар`;
- **атрибуты** — свойства сущностей, например `id`, `название`, `цена`;
- **связи** между сущностями, например «Пользователь оформляет Заказ».

Этот уровень подходит для обсуждения архитектуры с заказчиком, аналитиками и командой, так как он понятен даже неподготовленному участнику.

---

### 2. Логический уровень — выбор нотации зависит от типа СУБД

На логическом уровне модель данных уточняется и должна учитывать особенности выбранного хранилища данных.

#### 2.1. Для реляционных БД — Crow’s Foot

Для проектирования реляционных баз данных рекомендуется использовать нотацию **Crow’s Foot**.

Она позволяет описать:

- таблицы и их поля;
- первичные ключи;
- внешние ключи;
- кардинальность связей: один-к-одному, один-ко-многим, многие-ко-многим;
- обязательность или необязательность связей.

Пример использования:

- `Пользователь` может иметь много `Заказов`;
- `Заказ` может содержать много `Позиций заказа`;
- `Товар` может входить в разные `Позиции заказа`.

Crow’s Foot хорошо подходит для проектирования нормализованной реляционной схемы.

---

#### 2.2. Для документных / NoSQL БД — UML Class Diagram

Если в качестве хранилища используется документная база данных, например **MongoDB**, вместо классической реляционной ER-нотации удобнее использовать **диаграмму классов UML**.

Class Diagram позволяет описать:

- сущности как классы или документы;
- поля документов;
- вложенные объекты;
- массивы;
- ссылки между документами;
- границы агрегатов.

Например, вместо отдельных таблиц `Заказ` и `Позиции заказа` в MongoDB заказ может быть представлен как один документ со вложенным массивом позиций:

```text
Order
- orderId
- userId
- createdAt
- status
- items[]
  - productId
  - quantity
  - price
```

Такой подход лучше отражает особенности документной модели данных, где связанные данные часто хранятся внутри одного документа.

---

## Итоговая рекомендация

При построении модели данных в System Design рекомендуется придерживаться следующего подхода:

1. **Концептуальный уровень** — использовать **диаграмму Чена** для описания сущностей, атрибутов и связей предметной области.
2. **Логический уровень для реляционных БД** — использовать **Crow’s Foot**, если данные хранятся в SQL-базе.
3. **Логический уровень для MongoDB и других документных БД** — использовать **UML Class Diagram**, так как она лучше отражает структуру документов, вложенные объекты и агрегаты.

Такой подход позволяет сначала спроектировать понятную бизнес-модель данных, а затем адаптировать ее под конкретный тип базы данных.
